01 — Executive Summary

What Can Be Achieved

Four things Claude Code can do for RGB today — before any engineering work by the Association.

CAPABILITY 01

Issue an RGB Token End-to-End

Generate a contract, anchor it to a Bitcoin UTXO, and save the consignment file on the user's computer for client-side validation. The full issuance flow — from zero to a working RGB20 token — executable from a single conversation.

CAPABILITY 02

Program in Rust and Contractum

RGB's entire toolchain is Rust. Claude programs in Rust natively. It also writes and debugs Contractum — RGB's custom smart contract language — using live compiler feedback and fetching current specs directly from rgb.tech during the task.

CAPABILITY 03

Guide a Non-Programmer Through Issuance

The user answers three questions: name, ticker, supply. Claude handles every install, every command, every config file — and explains each step in plain language. No code knowledge required from the user.

CAPABILITY 04

Be Made RGB-Aware by the Association

Two actions — publishing a CLAUDE.md in the RGB-WG repos and an llms.txt on rgb.info — are enough to correct every AI coding tool for every developer who touches RGB. Both are content tasks: no engineering required.

The Highest-Impact Action: an MCP Server for RGB

MCP (Model Context Protocol) is Anthropic's open standard for connecting AI tools to live data sources. Think of Claude as a very smart consultant who studied a lot of books. An MCP server is giving that consultant a direct line to your company's internal library — so instead of working from memory, they look things up live every time.

Without an MCP server, Claude answers RGB questions from training data that may be months old and mostly cites rgb.tech. With an MCP server pointing to rgb.info, every developer using Claude Code gets the Association's documentation — automatically, without anyone doing anything extra. The correction happens at the source, not one Stack Overflow answer at a time.

Building the server requires a developer. Specifying what it serves, writing the documentation it exposes, and coordinating maintenance — that is the Association's content role.

03 — Answer to Q1

Capabilities & Requirements

RUST

Fully capable

RGB's toolchain — rgb-core, rgb-lib, rgb-std — is written in Rust. Claude reads, writes, and debugs it natively, including all SDK calls needed for issuance.

  • Define a contract (RGB20 fungible token schema)
  • Build a genesis (the issuance transaction)
  • Anchor it to a Bitcoin UTXO via single-use seals
  • Produce and save the consignment file for client-side validation
CONTRACTUM

Capable with live feedback

Contractum is RGB's custom smart contract language. Claude knows the syntax and semantics and can write contracts — fixing errors iteratively from compiler output.

  • Write Contractum contract source files
  • Debug from compiler error output
  • Fetch current specs live from rgb.tech/program and GitHub during the task
  • Cannot run the compiler remotely — it must be installed locally
CLIENT-SIDE VALIDATION DATA

Standard operation

Claude writes the logic to serialize and save stash and consignment files to disk. This is Rust file I/O — nothing exotic. The result is a portable proof of ownership stored locally, with no server dependency.

What needs to be installed on the machine

Tool Why it's needed
rgb CLI Installed via cargo install rgb — the main issuance interface
Bitcoin node Regtest is enough — no real BTC required for testing
Funded UTXO The genesis seal must close a real UTXO (fake coins work on regtest)
rgb-lib crates Added to Cargo.toml — provides the higher-level Rust SDK
Contractum compiler Only needed when writing .contract source files directly; Rust macros work without it
HOW CLAUDE LEARNS CURRENT CONTRACTUM SYNTAX

Claude does not rely on training data for fast-moving specs. It uses live web fetching to read rgb.tech/program and the Contractum GitHub spec during the task. It can also read any spec file dropped into the project folder. Three mechanisms work in combination: live doc fetching, local file reads, and iterative compiler error fixing.

04 — Answer to Q2

Guiding a Non-Programmer Through Issuance

The user answers three questions and approves the installs. Claude does everything else — and explains each step in plain language.

  1. 01
    Install Rust. One command, run directly in the conversation so Claude sees the output and handles any errors before proceeding.
    curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
  2. 02
    Install the RGB CLI. cargo install rgb-contracts --all-features — takes a few minutes. Claude explains what is compiling and why.
  3. 03
    Install Bitcoin Core in regtest mode. No real money involved. Claude writes the config file automatically — the user never edits it manually.
  4. 04
    Start the local fake Bitcoin network. Claude runs four commands: start the node, create a wallet, get an address, mine 101 blocks to it. In plain English: "I'm creating a fake Bitcoin network on your computer so we have something to anchor your token to."
  5. 05
    Three questions, then issuance. What do you want to call your token? What ticker? How many? Claude runs the issuance command and returns a contract ID and a consignment file.

What the user ends up with

~/.rgb/
  contracts/
    rgb1abc...xyz.yaml     ← your token definition
  stash/
    consignment-MYT.rgb    ← your client-side proof of ownership

Claude explains what each file is, what to back up, and what to do next — for example, transferring to Iris or BitMask on testnet.

HONEST LIMITS
  • First run takes 20–40 minutes (Rust compiling)
  • Linux or Mac preferred — Windows requires extra steps
  • Mainnet requires a small amount of real BTC to anchor the token
05 — Answer to Q3

Sources Used

Claude fetches documentation live during the task — not from training data. This matters for RGB because the protocol evolves fast and version differences are consequential.

Primary — fetched live
rgb.tech/docs CLI reference and command syntax
rgb.tech/program How to write contracts in Contractum
rgb.tech/install Installation instructions for the CLI and node
github.com/RGB-WG/rgb The CLI tool itself — README has usage examples
github.com/RGB-WG/rgb-schemata Standard contract schemas including RGB20
github.com/RGB-WG/rgb-lib Higher-level Rust abstractions for issuance and transfer
docs.rgb.info The Association's user-facing documentation portal
Secondary
blackpaper.rgb.tech Technical spec — client-side validation mechanics, single-use seals
rgbfaq.com Community FAQ — edge cases and common errors
LNP/BP YouTube Video walkthroughs of issuance flows
WHAT CLAUDE DOES NOT USE
  • General Bitcoin tutorials — they do not cover RGB
  • rgb.tech's security notice as the final word on v0.11.1 — cross-referenced with rgb.info and the Association's position
  • Stack Overflow — almost no accurate RGB content exists there yet (which is exactly the gap identified in the Part 1 audit)
06 — Answer to Q4

Making Claude Code RGB-Aware: Four Levers

What the Association needs to do — as a content role, not an engineering role — to make every AI coding tool default to rgb.info and v0.11.1.

LEVER 01

CLAUDE.md files in the RGB-WG repos

Claude Code reads a file called CLAUDE.md automatically whenever it opens a project. A plain-text file placed in the RGB-WG GitHub repos sets the correct context for every Claude session inside that repo — right version, right docs, right caveats — without the developer doing anything.

Example content: "This project uses RGB v0.11.1 (rgb.info). Do not reference rgb.tech or any pre-v0.11 documentation. Contract schema reference: [link]. CLI reference: [link]."

No engineering required. This is a content task, executable in week one.

Who: you Timeline: week 1 Impact: immediate for Claude Code users
LEVER 02

llms.txt on rgb.info

An emerging standard gaining fast adoption: a file at rgb.info/llms.txt containing clean, structured plain-text documentation formatted for AI tools to consume. AI coding tools that support it — Claude, Cursor, and others — fetch it automatically when users ask about RGB.

The result: always current documentation, always the right version, served to every AI coding session involving RGB. One publication, continuous effect.

You write the content. One developer publishes the file.

Who: you + 1 dev Timeline: week 1 Impact: broad, fast
LEVER 03

Restructure docs for AI consumption

Current RGB docs are written for humans reading linearly. AI tools extract information more reliably when documentation follows four rules:

  • One concept per page with a clear title
  • Explicit version tags at the top — Applies to: v0.11.1
  • Code examples that actually run, not pseudocode
  • Explicit "do not confuse with" notes — RGB vs RGB++, rgb.tech vs rgb.info

Pure content work. Restructuring the existing docs with these principles improves AI answers across all platforms long-term.

Who: you Timeline: month 1 Impact: long-term, cumulative
LEVER 04

MCP server for RGB documentation

MCP (Model Context Protocol) is Anthropic's open standard for connecting Claude to live data sources. When a developer asks Claude Code to issue an RGB token, Claude pulls the current v0.11.1 spec live from the server — always the right version, never stale training data.

A developer builds the server — or you build it with Claude Code, with no programming experience required. The Association's content role is to specify what it serves, write the documentation it exposes, and coordinate maintenance. Being the first Bitcoin protocol with an MCP server is a concrete, memorable signal to the entire AI-tools ecosystem.

Who: developer, or you + Claude Code Timeline: month 2+ Impact: highest of all four
