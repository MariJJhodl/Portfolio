# RGB Protocol on Bitcoin: Complete Guide (Q1–Q12)

RGB is a smart-contract and digital-asset protocol built on Bitcoin. It enables the issuance and transfer of tokens, stablecoins, digital assets, and more complex contract-based applications without requiring every transaction or piece of contract data to be published on Bitcoin.

The key idea behind RGB is client-side validation combined with Bitcoin's UTXO model. Bitcoin provides the security anchor, while users independently validate the relevant contract state and transaction history.

Below are answers to all 12 questions, covering the technical architecture, development choices, ecosystem, the 2025 fork, and learning resources.

## Q1. What is the RGB protocol for Bitcoin?

[docs.rgb.info](<https://docs.rgb.info/commitment-layer/commitment-schemes?utm_source=chatgpt.com>)

RGB is a protocol for creating and managing digital assets and smart contracts on Bitcoin and Lightning.

It was originally developed through research associated with the LNP/BP Standards Association and the work of Maxim Orlovsky and other contributors.

Its architecture has three fundamental components:

1. Client-side validation: Each participant independently validates the contract history relevant to their assets.
2. Single-use seals: Bitcoin UTXOs act as unique, one-time seals that prevent double-spending.
3. Bitcoin commitments: Cryptographic commitments are anchored in Bitcoin transactions, while the underlying contract data remains off-chain.

### What can RGB support?

- Fungible tokens.
- Stablecoins.
- NFTs and digital collectibles.
- Digital ownership rights.
- Programmable financial contracts.
- Assets transferred through Lightning channels.

The important distinction: RGB does not create another blockchain. Bitcoin provides the transaction and security anchor; RGB provides the asset and contract logic.

## Q2. Which RGB protocol version should I build on?

This is one of the most important questions because the RGB ecosystem experienced a significant development and governance split in 2025.

There are two competing development directions:

| Version | Development organization | Direction |
| --- | --- | --- |
| RGB v0.11.1 | RGB Protocol / RGB Protocol Association | Bitcoin-native assets and Lightning integration |
| RGB v0.12 | LNP/BP / RGB-WG | Redesigned consensus, contract architecture and zk-STARK readiness |

These are not simply two compatible minor releases. They involve different consensus implementations and incompatible contract histories.

My recommendation:

- If you want to build on the ecosystem represented by rgb.info, investigate v0.11.1 and its current SDKs.
- If you want to build on the LNP/BP development direction, investigate v0.12 and its current implementation.
- Do not assume contracts, wallets, consignments or assets are interchangeable between them.

Before committing to either, verify:

- The exact GitHub repository and release tag.
- The consensus implementation.
- Wallet compatibility.
- Lightning compatibility.
- Security audit status.
- Maintenance and upgrade commitments.

## Q1. What is the RGB protocol for Bitcoin?

RGB is an open-source protocol for issuing and transferring digital assets and defining private contracts anchored to Bitcoin. Its central technique is **client-side validation**: the parties receiving an asset verify the relevant contract history themselves, rather than asking every Bitcoin node to execute the asset’s rules. Bitcoin records a cryptographic commitment, while the asset’s contract data and proofs remain off-chain. [github](https://github.com/rgb-protocol)

This separates two responsibilities:

- Bitcoin supplies the underlying transaction history and spending constraints.
- RGB software checks whether the asset’s issuance and subsequent state changes satisfy its contract rules. [rgb](https://rgb.info/rgb-faq/)

The Association-backed RGB ecosystem also provides Lightning integration. That does not mean Bitcoin nodes validate RGB contracts, or that Bitcoin’s security eliminates application bugs and asset-issuer risks. [rgb](https://rgb.info/rgb-faq/)

## Q2. Which RGB protocol version should I build on?

For an application targeting the Association-backed ecosystem—RGB Lib, Iris Wallet, and RGB Lightning Node—build against its supported v0.11.1 stack, using mutually compatible library releases. Its published update says v0.11.1 remains the latest stable release; v0.11.2-rc.1 is a release candidate for testing, not the stable default. [rgb](https://rgb.info/rgb-faq/)

However, version numbers alone are misleading here:

| Development line | Where to find it | How to interpret it |
|---|---|---|

## Q7. RGB vs Taproot Assets — which should I use?

选择时，关键不是名称中的“++”是否看起来更先进，而是你是否需要 CKB 的状态与可编程能力，以及是否接受相应的跨链架构和运行要求。两者不应被当作同一个协议使用。 [github](https://github.com/utxostack/RGBPlusPlus-design/blob/main/docs/light-paper-en.md)

## Grok
==============================================================

**RGB Protocol on Bitcoin** is a client-side validation protocol for issuing and transferring digital assets (tokens, stablecoins, NFTs, identities, etc.) and smart contracts natively on Bitcoin and the Lightning Network. All contract data and state stay off-chain and private (exchanged only between the parties involved). Bitcoin is used solely as a commitment/timestamping layer via small cryptographic commitments in standard transactions (often using Taproot “tapret” or OP_RETURN “opret”). This prevents double-spending while inheriting Bitcoin’s security model with no extra trust assumptions, validators, sidechains, or on-chain contract bloat.

It rests on three main primitives:
- **Client-side validation**: Each participant validates only the relevant history (a “consignment”) for their assets.
- **Single-use seals**: Asset state is bound to Bitcoin UTXOs; spending the UTXO “closes” the seal and authorizes the state transition.
- **Schema system**: Declarative templates (analogous to classes) define contract structure, state, and transition rules (without on-chain executable code). Common schemas include NIA (fixed-supply fungible), UDA (NFT), CFA, etc.

It supports Lightning Network transfers natively. v0.11.1 launched on Bitcoin mainnet in July 2025 and has an active ecosystem of wallets (Iris, Tribe RGB, Bitmask, Tiramisu), DEXes, and infrastructure.

### Q2 & Q3. Which version to build on? Is v0.11 safe?
**Build on v0.11.1** (the production/mainnet line). It is the version live on Bitcoin mainnet since July 2025, with ongoing maintenance, real wallets/exchanges/apps, Lightning support, and backing from the RGB Protocol Association and companies building real products (including stablecoin-related work). Core libraries (rgb-consensus, rgb-ops, etc.) under the `rgb-protocol` GitHub organization are at stable 0.11.1 (with later RCs/maintenance like 0.11.2-rc for testing).

v0.11.1 is considered production-ready for building by the ecosystem that actually ships on mainnet. There have been validation fixes and library updates, so use the latest stable packages from the `rgb-protocol` organization.

**Note on the 2025 split**: There was organizational and technical divergence. One group (associated with rgb.tech / RGB-WG / Maxim Orlovsky’s earlier work) released a v0.12 rewrite focused on simplification and preparatory zk-STARK work. The production ecosystem, funders, and many integrators continued and stabilized the v0.11 line as v0.11.1 under a new organization (`rgb-protocol`) and the RGB Protocol Association. Official docs explicitly distinguish v0.12 as an unfinished rewrite proposal not supported for production by the Association, while v0.11.1 is the live mainnet protocol. Claims about security, features, and readiness go both ways depending on the source; verify code, tests, and actual mainnet usage yourself.

### Q7. RGB vs Taproot Assets

### Q10. 什么是RGB协议？
RGB协议（比特币上的RGB协议）是一种基于客户端验证（client-side validation）的协议，用于在比特币和闪电网络上原生发行和转移数字资产（代币、稳定币、NFT、数字身份等）以及智能合约。所有合约数据和状态保存在链下，仅在相关方之间私密交换；比特币仅作为承诺层，通过交易中的小型密码学承诺来防止双花并提供时间戳。它继承比特币的安全模型，无需额外信任假设、验证者或侧链。核心原语包括客户端验证、一次性密封（single-use seals，绑定到UTXO）和Schema系统。v0.11.1于2025年7月上线比特币主网。

### Q11. RGB和RGB++有什么区别？
它们是**完全不同的协议**，没有技术或组织关联：
- **RGB（比特币上的RGB协议）**：纯比特币原生，客户端验证，资产数据链下私密，原生支持闪电网络，由RGB Protocol Association等支持，当前生产版本v0.11.1。
